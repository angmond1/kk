# Claude Code Skill 빌드 가이드 (범용 방법론)

> 반복적인 업무(특히 **사내 웹 시스템·SaaS** 조작)를 Claude Code skill로 만들어 팀에 배포하는 일반 방법론.
> **특정 조직·개인에 종속되지 않게** 설계하는 원칙 중심이다. (구체 사례는 "메일 관리 skill"로 익명 인용)
>
> 이 문서는 다른 세션·다른 도메인에서도 같은 방식으로 skill을 만들 수 있도록 작성됐다. kiki에 국한되지 않는다.

---

## 0. 언제 skill로 만드나
- 절차가 명확하고 **반복**되는 업무
- 브라우저나 API로 자동화 가능
- 팀원이 **각자 자기 계정으로** 쓰면 가치 있는 것

---

## 1. 가장 먼저 — 정보 5분류 (이 방법론의 핵심)

skill을 "**누구나 자기 환경에서**" 쓰게 하려면, 다루는 정보를 5가지로 나눈다. 이 분류가 모든 설계의 출발점이다.

| 구분 | 내용 | 처리 |
|------|------|------|
| **A. 내장 (모든 환경 공통)** | 도메인 지식·업무 절차·재사용 코드·판별 정책 | skill에 박음 |
| **B. 런타임 자동조회** | 사람마다 다른 값(폴더/리소스 ID, 본인 계정 정보 등) | 코드가 실행 때 자동 조회 |
| **C. 환경별 본인 준비** | 로그인 세션, 도구(브라우저 확장 등) 설치 | 각자 본인이 (credential 아님) |
| **D. 개인 선택 (1회 설정)** | 선호·커스텀·개인 규칙 | 로컬 config (repo 밖) |
| **E. 절대 격리** | 토큰·비번·개인키, 특정인 식별자, 개인 학습 내역 | skill에 **안 넣음** |

→ "**자동으로 되는 것**" = A+B / "**개별로 준비할 것**" = C(필수)+D(선택) / "**유출 방지**" = E

> 가장 흔한 실수: 내 계정의 ID·폴더·발신처 학습을 skill에 그대로 박는 것. 그러면 남이 못 쓰거나 내 정보가 샌다. **B(런타임 조회)와 D(로컬 config)로 빼는 게 범용화의 본질.**

## 2. 인증 · credential 전략

- **세션 쿠키 우선**: 대상이 사내 SPA의 내부 API라면 보통 **브라우저 로그인 세션(쿠키)**으로 동작한다 → API 토큰 자체가 불필요 → **유출 위험 0**. 각자 본인 로그인만 하면 됨.
- **토큰은 on-demand**: 공식 API가 꼭 필요한 기능만, 그 작업을 요청받는 순간에 발급 안내. 설치 때 미리 묻지 않는다.
- **credential은 skill·repo에 절대 금지**. 필요하면 각자 로컬 `.env`에서만 읽고 값은 박지 않는다.

> 점검: 만들려는 기능이 "브라우저로 클릭해서 하는 일"이면 세션 쿠키로 토큰 없이 가능할 확률이 높다. "서버/스크립트로 무인 자동화"면 토큰이 필요하다.

## 3. skill 구조

```
skill-name/
  SKILL.md                 # frontmatter(name+description) + 워크플로우 + 안전규칙
  references/              # 정책·API 레퍼런스 (.md) — SKILL.md에서 링크
  scripts/                 # 재사용 코드 (credential-free)
  skill-name.config.example.json   # 개인설정 템플릿 (실제 config는 repo 밖)
```

- **frontmatter는 `name`(kebab-case) + `description`(트리거 표현 필수)만.** 복잡한 설정은 본문 표나 references로.
- `description`에 "**사용자가 ~ 요청 시**", "~ 키워드 포함 시" 같은 **트리거 문구**를 반드시 넣는다(스킬 자동 활성 정확도).
- **config는 repo 밖**(`~/.claude/<패키지>/<skill>.config.json`)에 둔다 → `git pull` 충돌·유출 방지, 형제 skill과 공유.

## 4. 미지의 내부 API 다루기 (실전 핵심)

사내 SPA의 내부 API는 공개 문서가 없다. 다루는 절차:

1. 브라우저 **DevTools → Network 탭**으로 실제 동작을 한 번 수행하며 요청 관찰 (URL·method).
2. **요청 본문(payload)은 사용자가 1회 캡처해 전달** — 자동화 도구로는 보안상 request body를 못 읽는 경우가 많다. (DevTools에서 "Copy as fetch" 또는 Payload 원문)
3. 확보한 형식으로 **생성→확인→삭제 테스트**를 돌려 endpoint·body를 확정한다.
4. 확정 형식을 코드 + 레퍼런스에 **함정과 함께 기록**한다.

> 자주 만나는 함정(기록해 둘 가치): 배열 POST가 첫 1건만 처리됨 / GET 파라미터(page 등) 누락 시 빈 응답 / 특정 조건(제외 필터 등) 미지원 / endpoint 경로가 추측과 다름 / **검색조건을 넣어도 서버가 무시하고 전체를 반환**(→ 응답에서 직접 필터해야 함) / 금액 등이 `{hi,lo}` 같은 객체로 옴. 이런 건 **시행착오 + DevTools 캡처**로만 풀린다.

### ⭐ SPA/사내시스템 backend 직접 호출 (좌표 탈피 — 범용 PC 동작의 핵심)
화면이 **좌표 클릭 기반**(NEXACRO·구형 ERP 등)이라도, 그 화면이 부르는 **backend 요청을 재현**하면 좌표·해상도 없이 데이터를 얻는다. 사람마다 모니터·해상도가 달라 좌표 클릭은 깨지기 쉬우므로 **fetch 직접호출이 범용 skill 의 정석**이다(좌표는 fallback):
1. **XHR/fetch 후킹**으로 화면 동작 1회의 endpoint + 요청 body + 응답을 캡처(브라우저 안에서 가로채면 사용자 F12 없이도 됨).
2. 인증이 페이지 **전역 변수/쿠키**에 있으면(예 세션 토큰) 추출해 재사용. 보통 **세션 쿠키(`credentials:'include'`)** 만으로 충분(토큰 불요).
3. fetch 직접호출로 함수화 → 검색조건은 파라미터만 바꿔 모든 조합 조회. (한 화면만 열려 있으면 다른 화면 endpoint 도 같은 탭에서 호출 가능)
4. ⚠️ 일부 backend 는 **호출 순서/세션 상태 의존**으로 직접 fetch 가 빈 응답일 수 있음 → **좌표 fallback 병행**("어떻게든 성공": fetch → 좌표(zoom 으로 위치 찾기, 고정좌표 금지) → 그래도 안 되면 사용자 안내).
5. 출력에 쿠키·토큰이 섞이면 자동화 도구가 `[BLOCKED]` 로 차단할 수 있으니 **핵심 필드만** 반환.
6. 환경 의존 **모달 팝업**(파일접근 보안 경고 등)이 자동화를 막을 때 — 표준 윈도우 컨트롤이 아닐 수 있다(WPF·커스텀 렌더 → 버튼 클릭·접근성 API 모두 실패). **키 입력 액셀러레이터**(예 `Alt`+밑줄글자) + **별도 프로세스 watcher**(메인이 블록돼도 계속 도는; 같은 프로세스 스레드는 동기 호출 중 안 돎)로 우회. 단축키 동작은 환경마다 다르니 **첫 실행 점검** 단계를 둔다.
7. 브라우저 JS 실행 도구가 REPL 이면 **top-level `await` 가 막힐 수 있다** → `(async () => { ... })()` async IIFE 로 감싼다.
8. ⭐ **보조 파라미터가 응답 형태(집계 레벨·범위)를 바꾼다** — 빈/부분 응답이면 추측 말고 화면이 보낸 request body 의 **실제 파라미터 값**을 캡처해 그대로 재현하라. 전체조회용 특수 상수(예 연도칸에 `9999`)나 필수 보조키(분류·구분 코드)가 숨어 있어, 그게 빠지면 세부행만/빈값이 온다. (직접 시도한 추측값으로 빈 응답이 나도 "fetch 불가"로 단정 X)
9. ⭐ **"응답에 값이 없다"고 속단 금지** — 화면이 표시하는 값은 거의 backend 응답 어딘가에 있다(client 계산으로 단정 X). 원하는 값(예상 수치)을 **raw 응답에서 문자열 검색**해 어느 endpoint·dataset·컬럼·행에 있는지 역추적하면, 잘못 보던 컬럼/레벨/파라미터가 드러난다.
10. **같은 라벨이 여러 집계 레벨 행에 중복** — 합계/소계/세부가 같은 명칭을 가질 수 있다 → **레벨 구분 필드로 필터**(안 하면 세부값으로 오집계되고 호출마다 값이 흔들린다).
11. **팝업이 별도 window 면 그 window 에도 후킹** — `window.open` 후킹으로 팝업을 포획하고, 팝업 생성 *즉시* 그 window 의 XHR 프로토타입을 후킹해야 팝업 backend 호출(endpoint·body·resp)을 잡는다. 부모 탭 후킹만으론 안 잡힌다. (브라우저 안에서 가로채니 사용자 F12 불요 — *요청 전에 이미 잡힌 것부터 분석*)

12. ⭐ **쓰기/제출 화면은 fetch insert 대신 화면 컴포넌트 직접제어가 실용적일 수 있다** — 조회는 fetch 가 깔끔하지만, 제출(insert)은 backend 가 호출순서·세션상태에 의존해 fetch 재현이 어려울 때가 많다. 이때 팝업 포획 후 그 화면의 컴포넌트 API(예 NEXACRO `application.popupframes.<팝업>.form` 의 `set_value`/`dataset.setColumn`)로 값을 직접 채우고 **제출(신청)버튼은 사용자**가 누르게 한다(좌표 아님 — form 객체 접근이라 해상도 무관). fetch insert 로 가려면 제출 1회의 endpoint+body 를 XHR 후킹으로 캡처해야 한다.
13. ⚠️ **네이티브 모달(alert/confirm/파일 다이얼로그)이 뜨면 그 탭 CDP 전체가 frozen** — `evaluate`·`screenshot` 이 모두 타임아웃나고 **사용자가 모달을 닫아야** 복구된다(자동화 도구엔 네이티브 다이얼로그 처리 API 가 없을 수 있다). 입력값이 모달을 유발하지 않게(예: 날짜칸에 휴일값 → '휴일 불가' 모달) **값을 사전 검증**하고, 떴으면 사용자에게 닫아달라 안내한다. 파일첨부 native dialog 도 같은 이유로 자동화 불가 → 사용자 수동.
14. **환율/외화 환산은 시스템 확정값** — 카드 앱·명세서의 원화 환산액은 *잠정*(매입 시점 환율에 따라 변동)이다. 검수·지급의 원화는 시스템(예: 카드영수증조회 화면)의 **확정 사용금액**을 쓴다. 잠정액을 그대로 쓰면 매입확정액과 수천원 차이날 수 있다.

15. ⭐ **분기 함수 사전 set 으로 modal frozen 회피** — "신규/생성" 같은 분기 함수는 카드구분·문서구분 등 **선택값이 비면 동기 modal**(`gfn_msg("X를 선택하세요")`)을 띄워 부모 탭 JS 가 frozen(`evaluate` 45초 타임아웃). 함수 소스를 먼저 읽어 **분기 키와 case 별 popup formname 확인** → 분기 키를 사전 `setColumn` 으로 채워두면 frozen 안 남. 예: `ds_search.setColumn(0,"DOC_CLS","G")` 후 `doNew("N")` → switch(gubun) 의 `case 'G'` 가 fam_0704_02 팝업 띄움. **시도 → frozen → 사용자에게 "modal 닫아주세요" → 소스 확인 → 사전 set 으로 재시도** 가 표준 사이클.

16. ⭐ **안전필터 우회 (base64 인코딩)** — 일부 브라우저 자동화 도구는 NEXACRO 함수 소스(`key=value` 패턴·URL·긴 ID 토큰 포함)를 보안상 `[BLOCKED]` 처리한다. 평문 `fn.toString()` 반환이 막히면:
    ```js
    btoa(unescape(encodeURIComponent(fn.toString())))   // 도구는 base64 통과시킴
    ```
    받아서 `atob` 디코드. **함수 분기·콜백·검증 로직을 코드 레벨로 읽는 게 자동화 설계의 출발점**이라 우회 수단이 꼭 필요. 짧게 보고 싶으면 라인 필터 후 base64.

17. ⭐ **NEXACRO 팝업 콜백 메커니즘 (`window.opener.{callbackFn}(oRtn)`)** — 선택 팝업(예산항목·과제·인명 검색 등)의 "선택확인" 버튼은 보통 `doDecision()` → `oRtn` 객체(선택값 + svcId + callbackFn) 구성 → **`new Function('window.opener.'+callbackFn+'('+JSON.stringify(oRtn)+');')()`** 로 부모의 콜백 함수 호출. 정합 반영 + 부모 측 검증(한도·정합성) 실행. **JS 로 직접 `setColumn` 우회는 거부됨** — NEXACRO 내부검증 alert(`"X는 ... 이어야 합니다"`)로 차단. 정합 경로:
    - 부모가 팝업을 정식 함수(`openBudgPopup()` 등)로 띄워야 `opener` 살아있음
    - 팝업 닫기 = `doDecision()` 정식 호출 (콜백 경유)
    - 직접 set 은 화면만 채울 뿐 저장 검증에서 막힘
    > 우회로 시작했다가 검증에서 막히면 — 우회 폐기하고 *정식 함수 호출 + 콜백* 경로로 돌아가라.

18. ⭐ **컴포넌트 walk + killfocus 동기화 (UI 값 vs 저장 값 분리)** — `form.components` 가 `Edit`/`TextArea` 등 입력 컴포넌트를 직접 노출 안 할 때 (Switch/Tabpage/PopupDiv/Import 중첩 안에 있음):
    ```js
    function walk(parent, name, depth=0){
      if(depth>5||!parent.components) return null;
      for(const cp of parent.components){
        if(cp.name===name) return cp;
        const r = walk(cp, name, depth+1); if(r) return r;
      }
      return null;
    }
    const comp = walk(F, 'dpstDispNm');   // 5단 중첩도 찾음
    comp.set_value(value);
    ```
    하지만 **`set_value` 만으론 저장 검증이 보는 데이터에 동기화 안 됨**(특히 import 된 공통폼·binddataset 없는 직접입력 컴포넌트) → 저장 시 "X를 입력하여 주시기 바랍니다" alert. 해결 = **`killfocus` 핸들러를 호출해 UI 값 → 저장 데이터 확정**:
    ```js
    F.<container>.common_onkillfocus.call(F.<container>, comp, {fromobject:comp, fromreferenceobject:comp});
    ```
    "set_value 했는데 저장에서 검증 실패" 패턴은 거의 다 이 동기화 누락. **set_value → killfocus 동기화 → 저장** 순.

19. ⭐ **별도 시스템 창은 자동화 도구 제어 밖 (MCP 탭 그룹 경계)** — 같은 NEXACRO `application` 을 공유하는 팝업(`window.open` + 같은 origin)은 부모 탭 JS 로 `application.popupframes.<팝업>.form` 접근해 제어 가능. 그러나 **별개 시스템**(예: 전자결재 ngw.kist.re.kr → KIST 통합정보 p.kist.re.kr 과 다른 도메인/시스템)이 `window.open` 으로 띄우는 창은 application 공유 X·MCP 탭 그룹 밖 → JS·스크린샷 모두 불가. 사용자에게 "이 화면은 직접 보고 확인/제출 부탁드린다" 안내가 정석. **사전에 그 화면이 필요한 데이터를 부모 탭에서 추출**(예: 계정책임자명 = `ds_rqstGrid.RDSBJEMPNM`)해 "[안내] {계정책임자} 결재선에 추가하세요" 같은 문구로 사용자 가이드.

20. ⭐ **임시저장 vs 결재상신 분리 + 가역성 confirm** — 같은 폼에 `bt_save`(임시저장, `APV_STAT_CD="000-010"`) 와 `bt_approval`(결재상신, `"000-020"` + 가통제 적용 + 별도 시스템 창) 이 별도면, **임시저장은 시연으로 자동 가능 / 결재상신은 사용자 마지막 confirm 필수**(되돌리려면 결재 회수). 자동화 단계를 명확히 분리:
    1. 입력만 — 안전, 항상 자동
    2. 임시저장 — 신청관리번호 발급, 사용자 첫 confirm
    3. 결재상신 — 실제 제출, 사용자 최종 confirm
    한 번에 `bt_approval` 직행 X. 사용자가 화면 검토할 시간 보장.

21. ⭐ **데이터 master vs UI 형식 분리 (엑셀 master 패턴)** — "사용자 형식"(예: 한글 hwp 별지1호)이 시스템 입력의 **중간 변환물**일 뿐이면, **데이터를 구조화된 master(엑셀·DB·JSON)에 두고 UI/시스템엔 변환·주입**하라:
    - 옛 패턴: hwp 양산 → 행정원이 보고 시스템에 수기 입력
    - 새 패턴: 엑셀 9컬럼(행=건/열=항목) master → 자동화 도구가 엑셀 읽어 시스템 직접 입력
    엑셀은 (a) 여러 건 한눈에 대조·중복 검사 (b) `openpyxl` 로 파싱 즉시 (c) 사용자도 손쉽게 편집. 한글 보관 선호 사용자는 옵션(`log_format: xlsx_only` / `xlsx_and_hwp`)으로 동봉 가능하지만 **자동화 도구는 항상 master 만 조회**. 도메인의 사용자 형식이 비정형(워드·hwp·캡처)일 때 master 추출 함수가 skill 의 최초 작업이 된다.

22. **사전결재 vs 회의록 같은 "계획 vs 결과" 충돌** — 시스템이 자동 연동(예: fam_0700 의 사전결재 button00 → 회의록 자동저장) 으로 **계획 값으로 결과 값을 덮어쓸** 때가 있다. **결과(회의록) 우선** 원칙 + 자동 연동 후 master 로 복원 + 저장 재실행. 차이값(인원 증감·시간·장소)만 사유 기재. 시스템 동작을 그대로 받지 말고 master 와 비교 후 결과 우선 복원이 정석.

23. ⭐ **집계/내역 화면의 "개인 귀속"은 한 컬럼만 보지 말 것** — 같은 표라도 행 종류에 따라 사람 이름이 다른 컬럼에 있다(예: 일반 지출은 '적요'에 사용자명·'신청인'은 대행 행정원, 외부 분석의뢰는 '적요'엔 항목명만·사용자명은 '신청인'에만). 한 컬럼만 필터하면 일부 유형이 통째로 0으로 누락 → **이름 후보 컬럼을 모두 합쳐 매칭**하고, 매칭 0이면 §4-9(raw 역검색)로 어느 컬럼·형식인지 확인. (KIST 2026-06-17: 예실대비표 개인집계에서 연구활동비2=시험분석료가 '적요'엔 분석명만·연구자명은 '신청인'에만 있어 적요필터로 전부 0 → 신청인 합산으로 해결.)
24. ⚠️ **자동화 브라우저의 DOM 팝업 연쇄 함정** — fetch 가 안 되는 화면을 DOM 팝업으로 우회할 때 흔한 3가지: (a) `(async()=>{})()` 결과가 `{}` 로 와 못 받음 → **전역에 저장 후 동기 read**, (b) **백그라운드 탭 throttle** 로 timer 가 늦어 연쇄가 매우 느리고 *부분 누락으로 틀린 값* → 창을 **foreground** 로, (c) **팝업 재오픈 시 빈 grid** → 페이지 navigate 리셋 + **로딩 polling**(행>0 될 때까지 대기) 후 파싱. fetch 로 풀리면 이 셋 다 안 겪으니, 내역 화면일수록 fetch endpoint 캡처를 우선.

25. ⭐ **그리드 셀클릭으로 여는 상세팝업은 "좌표" 말고 "핸들러 직접 호출"** — 화면마다 행 구성이 달라 좌표는 쉽게 어긋난다(한 번 밀리면 엉뚱한 팝업이 뜨거나 무반응). 프레임워크 폼 객체를 잡아 ① 그리드를 **바인딩 컬럼으로 식별**(`getBindCellIndex('body',<컬럼>)>=0`) ② **셀 인덱스도 조회해서** 사용(하드코딩 금지) ③ **행은 dataset 의 rowposition 으로 지정**(핸들러가 인자 row 가 아니라 *현재 행*을 보는 경우가 많다 — 안 하면 항상 첫 행이 열린다) ④ 화면 표시 순서 ≠ dataset 인덱스(세부행 섞임) 주의. 🔴 **닫기는 그 팝업이 제공하는 닫기 버튼으로만** — 프레임워크 내부 `close()`/`destroy()` 를 직접 부르면 모달 컨테이너가 잔류해 이후 모든 열기가 `already exists` 로 *조용히 실패*한다(에러도 팝업도 없어 추적 난이도 최상, 복구는 페이지 리셋). 팝업 종류마다 금액·날짜 컬럼명이 다르니 **합계>0 인 컬럼 자동 선택 + 날짜 빈 행=합계행 제외 + 상세합 vs 화면소계 검산**을 세트로.
26. ⚠️ **집계표의 일부 항목은 애초에 개인 귀속 데이터가 없다** — "특정 인물이 쓴 금액"을 물어볼 때, 항목에 따라서는 월별 *흡수/풀링* 한 줄로만 기록돼 개인명이 아예 없다(예: 정규직 인건비·학생인건비 풀링제). **없는 건 없다고 명확히 말하고 대체 경로(인사·급여·참여율 화면)를 안내**하라 — 억지로 추정하면 오답이 된다. 반대로 간접비라고 건너뛰면 안 되는 것도 있다(특허비처럼 적요에 성명이 박힌 항목) → **직접비만 보지 말고 전 항목을 훑은 뒤 포함 여부를 사용자에게 확인**.
27. 🔴 **브라우저 도구가 여럿이면 '로그인이 있는 쪽'을 명시해서 쓴다** — 호스트 앱이 자체 내장 브라우저를 기본으로 붙여 주는 경우, 이름이 비슷한 도구(`navigate`/`browser_batch`/`computer`)가 두 서버에 동시에 있다. 사용자 세션(SSO)은 사용자 브라우저 확장 쪽에만 있으므로 skill 문서에 **서버를 못 박고**, 배치 도구도 같은 서버 것을 쓰라고 적는다. 섞으면 로그인 안 된 빈 창이 열리고 모호한 에러만 난다.
28. ⭐ **재수집은 증분으로** — 비싼 드릴다운(팝업 N개)을 매번 전수로 돌리지 말고, 싼 요약값(비목별 총액·건수)을 직전 스냅샷과 먼저 비교해 **변한 곳만** 다시 연다. 재사용한 부분은 결과에 '재사용'으로 명시하고, 요약값이 같아도 내부가 바뀌는 경우(상쇄거래)는 caveat 로 남긴다. diff 수치는 반드시 두 스냅샷 파일에서 계산(대화 기억으로 쓰면 틀린다).
29. **도구 출력 필터는 '값'이 아니라 '키 이름'도 본다** — `authTk`·`token`·`cookie` 같은 단어가 반환 객체의 키에 있으면 길이·불리언이어도 차단될 수 있다. 민감값 존재 확인은 중립적 이름(`ready`)의 불리언으로.
30. **Windows 셸 함정 2종** — (a) `"C:\dir\"` 처럼 역슬래시로 끝나는 따옴표 경로는 bash 에서 `unexpected EOF` → `/c/dir/` 형식, (b) cp949 콘솔에서 python print 가 `—` 등으로 크래시 → 스크립트에 `sys.stdout.reconfigure(encoding='utf-8')` 를 기본 탑재.

**정체성 요소(2026-09-26 확정)**: 각 skill 첫 실행 첫 줄 "안녕하세요 🐱 kk-xxx 를 준비할게요." · 작업 보고 첫 줄 상황별 머리표 `😸 완료 — kk-xxx`(정상) / `😻`(확인할 것 없음) / `😼`(사용자가 할 일 남음) / `😺`(조회만) / `🙀 중단` / `😿 부분 완료` — 다크모드에서 보이는 노란 얼굴 계열만 쓴다(발자국·검은 고양이 금지) · 설치 스크립트 끝 `=^.^=  kiki 설치 완료` · 브라우저 코어 주입 반환값 끝 ` =^.^=`. 기관·장소·과제명 자리표시는 혼란을 피해 `○○` 형을 유지하고, 정체성은 사람 이름 김키키에만 싣는다. 제출 문서·오류 문구에는 넣지 않는다.
배포 전 `tools/sync-check.sh` 의 개인정보 스캔과 함께 `git grep -E "홍길동|○○○"` 로 옛 자리표시가 남았는지도 본다.

## 10. LLM 사용량 최적화 원칙 (2026-09-27)
새로운 판단이 필요 없는 반복 작업은 **미리 짜 둔 스크립트·코어 함수**가 하고, LLM 은 판단(뜻 고르기·증빙 판독·비목·회의 주제·자산 판정)과 사용자 확인만 한다. 스크립트는 오류가 나면 조용히 멈추지 말고 한 줄 원인과 다음 행동을 출력한다(무한 재시도 금지).
| 반복 구간 | 전 | 후 |
|---|---|---|
| 브라우저 코어 주입 | 원본 .js 전체를 매번 전송 | `.min.js`(주석 제거본, `tools/build_min.py` 생성·`sync-check` 가 최신 검사) — 30~40% 적은 글자 |

**스크립트에서 LLM 으로 되돌린 것(2026-09-27 전체 흐름 검수, 실데이터 평가)** — 판단이 필요한 분류를 키워드 규칙으로 옮기면 틀린 결과가 '확정된 것처럼' 보여 더 위험하다:
- 회의비 업종 판별(`FOOD`/`RECEIPT` 정규식): 실제 카드내역 거래처 70곳에서 식당·카페의 절반만 잡고(순대·치킨 체인·카츠·BBQ·호르몬 등 누락, '식당·카페 아님?' 오표시) 호프·와인(주류 — 회의비 불가)을 후보로 올렸다 → 코드는 영수증함 여부·인원 하한·50만 초과만, 업종·명세서 판단은 LLM.
- 스팸 점수(`spamHints`): 받은편지함 3주치 226통에서 약탈적 저널·학회 모객·피싱 약 10통 중 1통만 '스팸의심', 지갑 펌웨어 피싱은 0점(거짓 안심) → 사내 발신만 걸러 외부 목록을 주고 판단은 LLM.
**검수 원칙(같은 검수에서 정함)**: ① 실패는 결과처럼 보이면 안 된다 — 포매터는 `null`(아직)·`{error}`(실패)·결과를 구분해 찍는다(세션 만료가 '카드 0건'·'규칙 없음'·'폴더 0개'로 보이던 결함) ② 브라우저→파이썬 파일 전달은 실행 번호(`run`)로 짝짓는다(같은 날 옛 다운로드를 조용히 쓰던 결함) ③ 쓰기 스크립트는 전부 검사 후 적용, 도중 실패는 되돌림 ④ 중대 자산(담당자표)은 가져오기가 기존 데이터를 줄이면 저장하지 않는다 ⑤ 오프라인 결함 주입 시험은 `tools/selftest.sh`.
스크립트로 옮기지 **않은** 것: fam_0704/0703 지급신청서 자동작성과 mcs_0003 검수창 입력(NEXACRO 쓰기 단계 — 화면 상태에 따라 분기가 많고 실제 상신 없이 끝까지 검증할 수 없어, 지금은 절차서의 검증된 JS 조각을 그대로 쓴다. 사용자 감독 하에 1건씩 실증하며 함수화할 것).
